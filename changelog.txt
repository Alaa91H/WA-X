WaEnhancer 1.8.0
Release date: 2026-10-05

A correctness release. HD Status works again and, for the first time, says what it
cannot do instead of failing quietly. The module scope is also confined to the two
applications WA X actually supports.

HIGHLIGHTS
- HD Status (HD Quality Images and HD Quality Videos) restored: the quality ceilings
  are back at full strength, the video size limit slider works again, and the real
  resolution and 60fps switches are hooked up instead of being decoration.
- HD Status now reports itself. Every resolved target, every applied override, every
  skipped step and every field a WhatsApp build does not have is written to the
  Xposed log, so "HD Status is not working" is now answerable from one logcat read
  instead of guesswork.
- The module scope no longer offers every installed application. The runtime accepts
  only WhatsApp and WhatsApp Business, so a scope edited by hand, or a future
  metadata mistake, cannot make the module run inside an unrelated app.
- One hook target failing no longer disables the rest. The image and video halves of
  HD Status install independently, and each override is applied on its own.

HD STATUS — ROOT CAUSE
HD Status had gone silently inert. It was not a single bug but a chain of five, and
none of them reported anything:

- The video upload ceiling was read as `max(preference, 90)`, using the seek bar's
  maximum as the floor. Because the bar tops out at 90 MB, the result was always
  90 and the slider could not change anything.
- The hooks behind "send video in real resolution" and "60fps" were deleted in a
  commit described as a simplification, while both switches stayed visible in the
  settings screen. Toggling them did nothing.
- The video ceilings were replaced by constants that had halved them: 3840 px to
  1920, and 24 Mbps to 10 Mbps, in both the field writes and the server props.
- Roughly twenty overrides were written as `fields["name"]?.setInt(...)` over a
  field map derived by parsing the class toString and pairing it with the
  dexkit field list by index. A renamed field became a no-op, and a mis-paired field
  of the wrong type threw from inside WhatsApp's own constructor.
- One resolver ended in `.first()` on a dexkit result. A single stale anchor raised
  an exception in the middle of the video block, so every override after it silently
  never ran — and the image half lived in the same method.

HD STATUS — WHAT CHANGED
- Video ceilings restored to 3840 px and 24 Mbps, the last known working values.
- The upload ceiling honours the preference across its whole 30 to 90 MB range and
  clamps a corrupt stored value instead of pinning it.
- Real resolution and 60fps hooked again. The requested size is clamped to an even
  dimension under the ceiling, because forcing a size the encoder rejects makes the
  transcoder fail the upload.
- Image ceilings unchanged: 51200 KB ceiling, quality 100, 6000 px longest edge, with
  the media preview crash guard that wide bitmaps require.
- Constant bitrate mode is set by resolving the enum constant by name, with an
  ordinal fallback, so it does not depend on one Android constant.
- The high-bitrate profile URL is cleared so WhatsApp does not reuse a low-bitrate
  encode it already produced.
- Single-transcode forcing, so WhatsApp does not downscale and then re-encode.
- The quality picker no longer latches its choice into the hooked app's prefs. Both
  gate paths are tried on every load, so a renamed gate recovers on the next
  launch instead of staying broken until WhatsApp's app data is cleared.
- Every WhatsApp target is resolved from an ordered candidate list, so a rename is a
  one-line change rather than a feature that quietly stops working.

MODULE SCOPE
- The hook entry point rejects any package outside the supported set before a single
  hook is installed. Previously it ran every hook stage for every package, and the
  update blocker installed a PackageInstaller hook in every process on the device
  except the system server.
- The supported packages are defined once and reused by the feature loader, the
  bridge access policy, the compatibility canary, the contact picker, the root
  diagnostics and both hook helpers.
- The recommended LSPosed scope is documented: it keeps the system framework entry
  because the package-visibility bypass and the install-downgrade patch run in the
  system server, and it omits the module's own package because LSPosed adds a legacy
  module to its own scope automatically. The module's own process is still hooked,
  which is what reports the module as active and makes its preferences readable
  from a hooked WhatsApp.
- The scope cannot be made static on the legacy Xposed API: LSPosed hard-codes
  `staticScope = false` for any module loaded through assets/xposed_init, and adding
  the modern META-INF files would make it ignore the legacy entry point and load
  nothing. This is recorded next to the metadata so it is not retried.

QUALITY GATES
- 756 test methods per flavor, 1512 executions, 0 failures, across 41 files.
- 25 new tests cover the HD Status decisions that previously could only be observed
  on a device: the candidate walk, the alias fallback, the upload-ceiling clamp and
  the output-size clamp. One of them caught a real defect immediately, a 1x1 request
  clamping to 0x0 because rounding down to an even dimension underflows.
- The compatibility matrix now follows the helper classes a feature constructs. It
  was reporting that HD Status needed no resolvers and read no preferences, and a
  sync had written that wrong state into the document. Re-syncing also corrects three
  features it had been under-reporting.

BUILD AND RELEASE
- One workflow, .github/workflows/ci.yml, remains the single source of truth.
- A normal run builds both flavors, runs the full verification suite, signs the debug
  APKs and uploads them as a CI artifact. It never creates a Release.
- Only a version tag publishes. The tag, the configured version and the version baked
  into each APK must be identical, and a tag whose release already exists fails
  instead of overwriting it.
- Release assets are exactly two files, both .apk; the staging directory is rejected
  if it holds anything else.
- Every artifact is verified with apksigner, and the version is read back out of
  each APK before it can be published.

COMPATIBILITY
- WhatsApp: 2.26.32.xx through 2.26.40.xx. WhatsApp Business: 2.26.32.xx through
  2.26.39.xx. The same code and the same anchors serve both packages.
- minSdk 28, targetSdk 34, compileSdk 37, ABIs arm64-v8a and armeabi-v7a.

KNOWN LIMITATION
The HD Status anchors could not be exercised against a live WhatsApp build in this
environment. What is guaranteed is the failure behaviour: a missing or renamed
target now costs exactly its own override, is named in the log with every candidate
tried, and never throws into WhatsApp. Two settings remain position-based rather
than name-based, inherited from the original implementation; both now refuse and
report instead of throwing or guessing.
