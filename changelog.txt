WA X 1.1.0
Release date: 2026-10-06

Per-target settings, and the Compose foundation they are built on. This is the release
where "one APK, two independent WhatsApp builds" stops being packaging and becomes
behaviour: a setting can now differ between WhatsApp and WhatsApp Business, and the
difference survives into the hooked process.

PER-TARGET SETTINGS
- Global remains the default for both builds. A target either follows it or has diverged,
  and the new screen makes that visible: pick Global, WhatsApp or Business and edit that
  one scope. 127 settings are available, 91 of them toggles.
- "Use Global" means no override is stored. It never means the stored value happens to
  equal the global one. Those are different, and collapsing them is a real bug: a user
  who set WhatsApp to Enabled while Global was already Enabled would see "Use Global" in
  the interface, and turning Global off would then silently turn their WhatsApp setting
  off with it. The tests assert exactly that case.
- A toggle offers three states: Use Global, On, Off. A setting that is not a toggle offers
  two: follow Global, or hold the value it has today.
- Per-target actions: copy every Global value onto this target, reset this target, reset
  every target. Resetting a target leaves Global untouched.
- An unreadable setting falls back to off rather than on, so a missing or corrupt value
  can never enable a hook.
- Keys the module uses for itself, and anything holding a credential or a file path, are
  deliberately not offered per target. Two copies of an API key is two places to change
  it.

HOW IT REACHES THE HOOKS
- One decorator sits under the preference object every feature already reads. Changing it
  changes several hundred reads without touching any of them, which is why this is a small
  change rather than an audit of the whole feature set.
- It answers only for keys it owns. It also sees WhatsApp's own preference reads, because
  it sits under the whole file, and it refuses anything that is not an override.
- A feature cannot write a target key. Writes from a hooked process go to Global and a
  target key is refused, so nothing inside WhatsApp can reconfigure the other build.
- Overrides are namespaced under `waxtarget.<code>.`. Global keeps its original key, so
  every setting configured before this release still reads back exactly as it was.
- A change made in the interface applies the next time WhatsApp starts. There is no
  cross-process notification yet; this is the one rough edge in the feature.

TWO BUGS THE TESTS CAUGHT BEFORE EITHER SHIPPED
- Values were being written with `putString` regardless of type. Every feature reads them
  through SharedPreferences, so the first read of a boolean setting would have thrown
  inside WhatsApp. It would have been a crash, not a wrong setting.
- The override lookup compared types with `Class.isInstance` against `Boolean::class.java`,
  which in Kotlin is the primitive `boolean` class and never matches a boxed value. Every
  override was silently invisible: the interface would have shown a saved setting that did
  nothing. The check is a type predicate now.

COMPOSE FOUNDATION
- Material3 1.4.0 through a pinned BOM, with the Compose compiler plugin. Stable
  versions only.
- `WaXTheme` provides light and dark schemes whose contrast ratios are stated in the
  source, dynamic colour on Android 12 and later, and a type scale tightened for dense
  settings screens.
- `TargetSettingsActivity` is the first Compose screen. The existing preference screens
  are unchanged and still work; converting a working preference screen and changing its
  behaviour in one commit is not a change worth making.
- `SettingKeyRegistry` is generated from the preference screens, so a renamed setting
  cannot silently become unofferable. The generator reads `app:key`, which is how these
  screens are written; a reader that only knows the `android:` namespace sees four keys in
  total and reports success.

SIZE, MEASURED RATHER THAN ASSUMED
- `material-icons-extended` was pulled in for two icons and added 30 MiB of vectors to a
  debug build. Removed in favour of the core icon set.
- What remains is the Compose runtime: debug APK 37.0 to 57.8 MiB, and the release APK
  users download 9.0 to 13.4 MiB.
- The size ratchet is still active. The step is recorded in
  `tools/baseline/APK_GROWTH_JUSTIFICATION.md` with its measurements, and the gate prints
  it; deleting that file restores the default limit.

QUALITY GATES
- 854 unit tests, 0 failures. 41 of them are new and cover the persistence contract, the
  tri-state, isolation in both directions between the two processes, type safety on reads
  and the refusal of cross-target writes.
- The formatting gate was extended to cover main source for the first time, which found
  173 files it had never inspected. All of it is now formatted.
- ktlint is told through its own configuration that composable functions are PascalCase,
  rather than by renaming them or by suppressing findings.

KNOWN LIMITATIONS
- A per-target change applies on the next WhatsApp start rather than immediately.
- No live-device verification was possible in the build environment. What changed is how
  settings are stored and read; the hooks themselves are untouched.
- The signing certificate still carries the previous project's name. It is the release
  key, held in CI, and changing it would mean a different signing identity for every
  future update.

WA X 1.0.0
Release date: 2026-10-06

The first release under the WA X name. The module is now one application that hooks
both WhatsApp builds, installs under a single package id, and carries its historical
attribution instead of its old name. The version number restarts here because this is a
different product identity, not a continuation of the old numbering.

BREAKING CHANGES — READ BEFORE UPGRADING
- The application id changed from `com.wmods.wppenhacer` to `com.wax.module`. Android
  treats that as a different application, so installing over the old build is not
  possible and the old settings are not carried over. Uninstall the previous version
  first, then install WA X and set your preferences again.
- WhatsApp Business is no longer a separate APK with its own id. There is one APK, and
  it hooks `com.whatsapp` and `com.whatsapp.w4b`. Remove the old Business module
  separately: it stays installed and hooked under its own package until you uninstall
  it, and two hooked modules writing to the same WhatsApp process is a support
  question nobody needs to have.
- The scope must be reviewed once after upgrading. The module no longer offers a
  per-flavor choice, and the recommended scope is the same for both targets.

IDENTITY
- Renamed from Wa Enhancer to WA X, including the application label, the root project
  name, the preferences file, the exported component names and the release artifacts.
- Neutral names replaced the acronym-heavy ones: `WppXposed` is `ModuleEntryPoint`,
  `WppCore` is `ModuleRuntime`, and `App` is `ModuleApplication`. The Xposed bridge
  types keep their upstream names, because they are not ours to rename.
- Every one of the 1447 old-brand references in the repository was rewritten in place.
  The classes that carry history were migrated rather than deleted, so a diff against
  the previous release still reads as the same code.
- Attribution is separated from maintenance. WA X is maintained by Alaa. The open
  source notices keep every previous contributor and the original project history, and
  the About screen says which is which instead of presenting a single author line.

ONE APK
- The two product flavors are gone. They existed for exactly one reason: separate
  application ids, and therefore separate preference files by accident rather than by
  design. That accident is now replaced by an explicit per-target settings model.
- One id, one APK, one version number. `app/build/outputs/apk/debug` contains a single
  file named `WA-X-<version>.apk`.
- The module scope array lists both target packages plus `android`, which is required
  for the package-visibility bypass and the settings bridge and is infrastructure
  rather than a target.
- CI was changed to match: it stages one artifact, verifies that exactly one APK was
  produced, and publishes exactly one release asset. A run that produces two APKs now
  fails instead of shipping both.

TARGET ROUTING
- The hook entry point resolves which WhatsApp build it is running inside from the
  process package name, rather than from which build the user installed. That is the
  change that makes a single APK correct rather than merely possible.
- The target is attached once per process before any feature runs, and features read
  settings through it. Nothing is cached across targets: a single shared
  "current configuration" object read by both processes is exactly how Business ends
  up applying WhatsApp's settings.
- A process that is not a supported target resolves to no target at all and exposes no
  settings snapshot, so a feature cannot read global defaults inside an unrelated
  application by accident.

SETTINGS MODEL — FOUNDATION, NOT YET THE SCREEN
- The settings model that per-target configuration needs now exists and is tested:
  Global holds concrete values, a target holds overrides, and each override either
  inherits or diverges. Resolution is one rule, in one place: target override, else
  global, else the documented default.
- "Use Global" means no override is stored. It never means the stored value happens to
  equal the global one. Collapsing those two is a real bug: a user who set WhatsApp to
  Enabled while Global was already Enabled would see "Use Global" in the interface, and
  turning Global off would then silently turn their WhatsApp setting off with it. The
  tests assert exactly this case.
- An unreadable setting falls back to false rather than to on, so a missing or
  corrupt value can never enable a hook.
- Backups carry Global and both targets in the existing v3 document, so a restore path
  is not duplicated and an older backup still reads. A malformed document is validated
  and flattened before anything is written, so a bad file cannot leave one target
  restored and another wiped.
- What is not in this release: the settings screen does not yet offer per-target
  overrides, and the module still reads one shared preference file at runtime. The
  model, the routing and the backup format are in place; the interface that writes to
  them is the next step. Nothing in this release claims behaviour that is not there.

QUALITY GATES — TWO GATES THAT WERE NOT GATEING
- The formatting gate was matching nothing in the main source tree. Its targets still
  pointed at the package tree from before the rename, which has not existed since the
  identity migration, so it had been checking the test sources only while reporting
  success. Every "formatting clean" claim before this release was unfounded for the
  module itself.
- With the target corrected, the formatter found 173 files it had never inspected and
  20 errors it could not fix automatically. All 20 are fixed: reflected type holders
  renamed to Kotlin conventions, JDK constants such as `java.lang.Void.TYPE` left
  alone, two wildcard imports expanded, several constants and one private singleton
  renamed to camelCase, four long lines wrapped and two duplicated documentation
  blocks merged.
- The regression gate read the removal of the second flavor as 785 deleted tests,
  because the suite used to run once per flavor and the recorded count was therefore
  twice the number of tests. The gate now compares tests per variant, which is what it
  was trying to measure. A deliberately deleted test still fails it; that was verified
  rather than assumed.
- Two tooling parsers broke on reformatted source and reported success with nothing to
  show for it: the feature extractor no longer found the plugin list after the
  formatter split one long assignment across two lines, and the baseline generator
  reported zero features for the same reason. Both match loosely now, and a full
  compatibility re-sync follows.

VERIFICATION
- 813 unit tests in 47 files, 0 failures, 0 errors, 0 skipped. The count is lower than
  the previous release's 1598 because the suite ran once instead of twice, not because
  a test was removed.
- 14 of those tests cover the new routing: that each process resolves to its own
  target, that neither reads the other's overrides, that a reload drops the cached
  snapshot, and that an unrelated package exposes no settings at all.
- Android lint holds at 313 baselined issues, the Unobfuscator assertion ratchet is
  unchanged at 27, and detekt and the compatibility matrix are clean.
- The built APK was inspected rather than assumed: one package, the expected label, a
  scope array containing both targets, and `assets/xposed_init` pointing at the new
  entry point.

KNOWN LIMITATIONS
- No live-device verification was possible in the build environment. The hook
  behaviour of 1.0.0 is unchanged from 1.8.0; what changed is packaging, identity and
  routing, none of which alter the hooks themselves.
- The static scope cannot be made hidden on the legacy Xposed API. LSPosed hard-codes
  `staticScope = false` for a module loaded through `assets/xposed_init`, and adding
  the modern metadata would make it ignore the legacy entry point and load nothing.
  This is recorded next to the metadata so it is not retried.
- The per-target settings screen and its persistence are not in this release. See the
  section above.

ATTRIBUTION
WA X is maintained by Alaa. This release carries forward the work and the notices of
the contributors listed in the About screen and in the open source notices; the rename
changed the product, not the people who built it.

WaEnhancer 1.8.0
Release date: 2026-10-05

A correctness release. HD Status works again and, for the first time, says what it
cannot do instead of failing quietly. The module scope is also confined to the two
applications WA X actually supports.

HIGHLIGHTS
- HD Status (HD Quality Images and HD Quality Videos) restored: the quality ceilings
  are back at full strength, the video size limit slider works again, and the real
  resolution and 60fps switches are hooked up instead of being decoration.
- HD Status now reports itself. Every resolved target, every applied override, every
  skipped step and every field a WhatsApp build does not have is written to the
  Xposed log, so "HD Status is not working" is now answerable from one logcat read
  instead of guesswork.
- The module scope no longer offers every installed application. The runtime accepts
  only WhatsApp and WhatsApp Business, so a scope edited by hand, or a future
  metadata mistake, cannot make the module run inside an unrelated app.
- One hook target failing no longer disables the rest. The image and video halves of
  HD Status install independently, and each override is applied on its own.

HD STATUS — ROOT CAUSE
HD Status had gone silently inert. It was not a single bug but a chain of five, and
none of them reported anything:

- The video upload ceiling was read as `max(preference, 90)`, using the seek bar's
  maximum as the floor. Because the bar tops out at 90 MB, the result was always
  90 and the slider could not change anything.
- The hooks behind "send video in real resolution" and "60fps" were deleted in a
  commit described as a simplification, while both switches stayed visible in the
  settings screen. Toggling them did nothing.
- The video ceilings were replaced by constants that had halved them: 3840 px to
  1920, and 24 Mbps to 10 Mbps, in both the field writes and the server props.
- Roughly twenty overrides were written as `fields["name"]?.setInt(...)` over a
  field map derived by parsing the class toString and pairing it with the
  dexkit field list by index. A renamed field became a no-op, and a mis-paired field
  of the wrong type threw from inside WhatsApp's own constructor.
- One resolver ended in `.first()` on a dexkit result. A single stale anchor raised
  an exception in the middle of the video block, so every override after it silently
  never ran — and the image half lived in the same method.

HD STATUS — WHAT CHANGED
- Video ceilings restored to 3840 px and 24 Mbps, the last known working values.
- The upload ceiling honours the preference across its whole 30 to 90 MB range and
  clamps a corrupt stored value instead of pinning it.
- Real resolution and 60fps hooked again. The requested size is clamped to an even
  dimension under the ceiling, because forcing a size the encoder rejects makes the
  transcoder fail the upload.
- Image ceilings unchanged: 51200 KB ceiling, quality 100, 6000 px longest edge, with
  the media preview crash guard that wide bitmaps require.
- Constant bitrate mode is set by resolving the enum constant by name, with an
  ordinal fallback, so it does not depend on one Android constant.
- The high-bitrate profile URL is cleared so WhatsApp does not reuse a low-bitrate
  encode it already produced.
- Single-transcode forcing, so WhatsApp does not downscale and then re-encode.
- The quality picker no longer latches its choice into the hooked app's prefs. Both
  gate paths are tried on every load, so a renamed gate recovers on the next
  launch instead of staying broken until WhatsApp's app data is cleared.
- Every WhatsApp target is resolved from an ordered candidate list, so a rename is a
  one-line change rather than a feature that quietly stops working.

MODULE SCOPE
- The hook entry point rejects any package outside the supported set before a single
  hook is installed. Previously it ran every hook stage for every package, and the
  update blocker installed a PackageInstaller hook in every process on the device
  except the system server.
- The supported packages are defined once and reused by the feature loader, the
  bridge access policy, the compatibility canary, the contact picker, the root
  diagnostics and both hook helpers.
- The recommended LSPosed scope is documented: it keeps the system framework entry
  because the package-visibility bypass and the install-downgrade patch run in the
  system server, and it omits the module's own package because LSPosed adds a legacy
  module to its own scope automatically. The module's own process is still hooked,
  which is what reports the module as active and makes its preferences readable
  from a hooked WhatsApp.
- The scope cannot be made static on the legacy Xposed API: LSPosed hard-codes
  `staticScope = false` for any module loaded through assets/xposed_init, and adding
  the modern META-INF files would make it ignore the legacy entry point and load
  nothing. This is recorded next to the metadata so it is not retried.

QUALITY GATES
- 756 test methods per flavor, 1512 executions, 0 failures, across 41 files.
- 25 new tests cover the HD Status decisions that previously could only be observed
  on a device: the candidate walk, the alias fallback, the upload-ceiling clamp and
  the output-size clamp. One of them caught a real defect immediately, a 1x1 request
  clamping to 0x0 because rounding down to an even dimension underflows.
- The compatibility matrix now follows the helper classes a feature constructs. It
  was reporting that HD Status needed no resolvers and read no preferences, and a
  sync had written that wrong state into the document. Re-syncing also corrects three
  features it had been under-reporting.

BUILD AND RELEASE
- One workflow, .github/workflows/ci.yml, remains the single source of truth.
- A normal run builds both flavors, runs the full verification suite, signs the debug
  APKs and uploads them as a CI artifact. It never creates a Release.
- Only a version tag publishes. The tag, the configured version and the version baked
  into each APK must be identical, and a tag whose release already exists fails
  instead of overwriting it.
- Release assets are exactly two files, both .apk; the staging directory is rejected
  if it holds anything else.
- Every artifact is verified with apksigner, and the version is read back out of
  each APK before it can be published.

COMPATIBILITY
- WhatsApp: 2.26.32.xx through 2.26.40.xx. WhatsApp Business: 2.26.32.xx through
  2.26.39.xx. The same code and the same anchors serve both packages.
- minSdk 28, targetSdk 34, compileSdk 37, ABIs arm64-v8a and armeabi-v7a.

KNOWN LIMITATION
The HD Status anchors could not be exercised against a live WhatsApp build in this
environment. What is guaranteed is the failure behaviour: a missing or renamed
target now costs exactly its own override, is named in the log with every candidate
tried, and never throws into WhatsApp. Two settings remain position-based rather
than name-based, inherited from the original implementation; both now refuse and
report instead of throwing or guessing.
